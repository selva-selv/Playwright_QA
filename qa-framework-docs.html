Page Object Model

How pages are structured — change selector once, fix everywhere

💡

Why POM?

If the app changes a button label or selector, you update it in ONE page class — not in every test file. Tests read like plain English. Selectors are never repeated.

Jira Integration

How bugs get created automatically — zero manual work

❌

FAILED Test → Jira Bug Card

Automatically creates a Bug in project KAN. Checks for duplicates first. Includes: environment, steps, expected, actual, error, screenshot path, severity, labels.

✅

PASSED Test → Nothing

Strict rule enforced in fixtures.ts. A passing test NEVER creates any Jira card. The afterEach hook only runs createJiraBug() inside an if (status === 'failed') block.

Bug Card Auto-Creation Flow

fixtures.ts → jiraHelper.ts
// fixtures.ts — afterEach hook
test.afterEach(async ({}, testInfo) => {
  if (testInfo.status === 'failed') {
    await createJiraBug(
      testInfo.title,                    // "TC109 - invalid email..."
      testInfo.error?.message,           // exact Playwright error
      testInfo.project.name,             // "chromium" | "firefox" | "webkit"
      screenshotPath                     // path to screenshot file
    );
  }
  // PASSED → STRICT RULE: DO NOT create any Jira card
});

Why 3 browsers?

The same UI bug may appear only in Safari or only in Firefox. By running all 3, we catch cross-browser issues automatically. If TC109 fails in Firefox but passes in Chrome — a separate Jira card is created for Firefox.

When a Test Fails — Full Flow

What happens automatically from failure to Jira

  1. Test Execution Fails Playwright assertion throws — e.g. expect(locator).toBeVisible() fails after 15 second timeout. Test is marked FAILED.
  2. Screenshot Captured Automatically Playwright saves a screenshot to test-results/<test-name>/test-failed-1.png. Configured via screenshot: 'only-on-failure' in playwright.config.ts.
  3. fixtures.ts afterEach Hook Triggers The afterEach hook checks testInfo.status === 'failed' — if true, calls createJiraBug() with test name, error message, browser and screenshot path.
  4. Duplicate Check in Jira findOpenBug() runs a JQL query: summary ~ "[BUG] TC109..." AND issuetype = Bug AND statusCategory != Done. If a card already exists — skip. Prevents duplicates.
  5. Jira Bug Card Created via REST API POST to /rest/api/3/issue with full ADF description: environment, steps, expected, actual result, exact Playwright error, screenshot path, labels, priority.
  6. All Tests Complete — Reporter Fires jiraReporter.ts onEnd() runs. Prints the full summary table and developer message to terminal. Then calls createTestRunSummary().
  7. Jira Task Created with Full Report One Jira Task card posted to KAN containing the full results table, pass/fail counts, developer message listing every failed test with its error and Jira bug key.
  8. Developer Receives the Jira Bug Card Developer opens the card, reads steps to reproduce, actual vs expected, and the exact Playwright error. Fixes the bug, comments on the card, replies "Fixed in commit #xxx".
  9. QA Re-Runs Tests to Confirm Fix After the developer fix is deployed, QA runs npx playwright test --grep "TC109". If it passes on all 3 browsers, the Jira card is closed.
📋

Strict Rules for the Team

Must follow — enforced in code

🚫

RULE 1 — PASSED = NO Jira card. Ever.

If a test passes, nothing is posted to Jira. No summary, no card, nothing. The afterEach hook is gated strictly on status === 'failed'.

🐛

RULE 2 — FAILED = One Bug card per test per browser

TC109 on Chromium = KAN-9. TC109 on Firefox = KAN-10. TC109 on WebKit = KAN-11. Three separate cards. Three separate bug IDs. Never merged.

🔍

RULE 3 — No duplicates

Before every bug creation, a JQL search checks if the same bug is already open. If yes — it is skipped. Re-running tests does not flood Jira with duplicate cards.

✅

RULE 4 — Fix ONLY the FAILED items

The developer message in Jira clearly separates FAILED (action required) from PASSED (no action needed). Developers should touch only what is listed under FAILED.

🔒

RULE 5 — Never commit .env

The .env file is in .gitignore. It contains real passwords and Jira API tokens. Never push it to Git. Use environment variables in CI/CD pipelines.
